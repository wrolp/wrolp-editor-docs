加密文件

AES-256-GCM 容器格式、三个入口、解锁与空闲锁、记住口令与草稿。

一个加密文件是一个自描述的容器，不是「加了密的 txt」：靠 magic 字节识别，与扩展名无关。

口令丢了，文件就丢了。 没有主口令、没有恢复码、没有后门。密钥由口令加上每个文件自己的随机 salt 经 Argon2id 派生，我们只存密文，不存任何能反推出口令的东西。

容器格式#

偏移  长度  内容
0     8     magic "WROLPENC"
8     1     格式版本（当前 1）
9     1     KDF id（1 = argon2id）
10    4     m_cost，单位 KiB（u32 LE）
14    4     t_cost（u32 LE）
18    4     p_cost（u32 LE）
22    16    salt，每个文件随机
38    12    nonce，每次写入重新随机
50    ...   AES-256-GCM(明文) || 16 字节 tag
  • 整个 50 字节头就是 AEAD 的 associated data。 改头里任何一个字节——包括把 m_cost 调小好让暴力破解 快一点——都会验证失败，而不是被照办。
  • 默认 KDF 参数是 Argon2id，m=65536 KiB、t=3、p=1，本机 release 构建实测约 70 ms 一次派生。参数写在头里， 所以改了默认值也不会让老文件打不开；保存沿用文件自己的 salt 与参数，不重新随机、不悄悄升降成本。 换口令是唯一换 fresh salt 的操作。
  • 写入一律是临时文件 + rename 的原子写：截断的密文不是「损坏」而是「没了」，这条没得选。
  • 大小上限按密文算，仍是 8 MiB。7.9 MiB 的明文加密后会超线并报 file_too_large，这不是编辑器坏了。
  • 只有 age（age-encryption.org/ 开头）会被明确认出来并拒绝，报 encrypted_foreign_format：不当文本打开、 不写回去。别的外来二进制仍是「解不出编码」那条错。不支持读写任何外来加密格式。

三个入口#

入口 行为
标签右键「加密另存为…」 先选路径再要口令，把当前 buffer 写成新容器；标签随即变成已加密、已解锁
资源管理器右键「新建加密文件」 要口令，写一个空容器，建好即打开；名字被占则拒绝
标签右键「修改口令…」/「移除加密…」 前者验旧口令再整文件重加密；后者验口令后把正文按 UTF-8 明文写回

新建时没写扩展名会补 .wrolpenc。用容器自己的扩展名而不是 .txt，是因为这种文件别的程序打不开——一个 承诺「我是文本」的扩展名只会诱导用户拿记事本去看一堆乱码。识别既然不靠扩展名，任何名字的容器都照样认得出来。 移除加密会把正文写成 UTF-8：原本是 GBK 的文件，移除之后就是 UTF-8 了。

改口令必须验旧口令，不能拿缓存里的钥代替：用户是在断言旧口令是什么，照一个错误的断言改口令等于把用户 锁在自己的文件外面。

解锁、缓存与空闲锁#

  • 口令只用一次：派生出密钥后口令本身就丢掉，密钥留在进程内存里按规范化路径索引，从不写盘、从不回前端。
  • 空闲锁在设置 → 加密 → 加密文件的自动锁定，默认 10 分钟，0 = 从不，上限 1440。到点先把草稿全部 冲刷（此刻还有钥，草稿能加密落盘），再丢掉内存里所有密钥。任何按键与点击都算「在用」，不只是打字。
  • 锁了不清屏，这是有意的取舍：屏上的明文是解锁期间合法读到的，锁的意思是「此后不能再保存、不能再落草稿」， 不是把文档从正在读它的人眼前拿走；换来的是不丢 undo 栈、不丢脏状态。代价是锁定后屏幕仍可被截图或肩窥。 锁定的标签编辑器变只读，保存会明确失败并弹口令框——不做静默丢弃。
  • 从没解密过的标签盖一层锁定提示，点它就重新问口令；不拿占位文本冒充内容，所以它不进 undo、不进比对、 不算脏。这类标签也不会被「从磁盘重新载入」清屏。
  • 会话恢复时加密标签排队问口令，一个对话框逐个来；输错就地重试，不出队。

记住口令（可选，默认不记）#

  • 只有勾了「在这台电脑上记住口令」才存，存进 Windows 凭据管理器：service 是 com.wrolp.editor， account 是 enc-<路径的 SHA-256 hex>。存的是路径摘要而不是路径，所以在凭据管理器里看不到你的文件名。
  • 上限 64 条，超了拒绝新的记住请求。这不是安全限制（凭据库本来就按用户加密），是为了让堆积可见。
  • 记住的口令解不开文件时（常见成因：文件在别处被重新加密过），算没有钥而不是口令错——照常弹框让你输， 同时把那条用不了的记住项删掉。用户什么都没输就报「口令错误」，是在说他没做的事。
  • 设置 → 加密 里能看到记住的条数并「全部忘记」。
  • 重命名即遗忘：文件改名后记住项被删掉，下次要手动输口令。凭据库的 account 是路径摘要、不可逆推回路径， 所以目录改名时无法判断哪些记住项该跟着搬，遗忘是唯一诚实的做法。会话内存里的钥则跟着路径搬家： 改名不动文件内容，正在编辑的文档不该因为改名就被锁掉。
  • 卸载不会清凭据管理器。 与右键菜单那条注册表项不同，enc-* 条目属系统级残留，卸载后仍在。要清就在 卸载前用设置页的「全部忘记」，或自己在凭据管理器里删 com.wrolp.editor 下的条目。

草稿与删除#

  • 加密文件的草稿用同一把文件密钥密封后落盘，形状是 {"v":2,"path":"<明文路径>","nonce":"<hex>","data":"<hex>"}，data 是原草稿 JSON 的密文。路径留在信封外 是有意的：路径不是秘密（它就是目录列表里的一个文件名），而留在明文侧才让重命名能在没有钥的情况下把 密文草稿搬到新 key 下。旧的无包装 JSON 草稿照样能读，不需要迁移步骤。
  • 是否加密由磁盘说了算（只读文件头 50 字节判定），不信前端传的标记：另一个窗口可能刚移除了加密， 文件也可能整个被换掉。
  • 没有钥时草稿写不下去 → 静默丢弃（草稿是后台行为，报错是打扰；主保存路径会明确失败并提示解锁， 不会无声丢数据）。读的时候没有钥 → 当「没有草稿」处理，但不删档：解锁后再打开同一文件自然又能解出来。
  • 草稿与文件共用一把钥，也就共用同一条 nonce 生日界（约 2^32 次写入）。编辑器量级不可达，记录在案。
  • 删掉一个加密文件时，kept/ 里那份救援副本是明文 —— 有意为之：一个打不开的救援副本不叫救援。 对话框文案会说清这一点。
